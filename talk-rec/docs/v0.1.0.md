# Talk Rec v0.1.0

동반차의 음성 기능 두 가지를 Pleos Connect AVD에서 검증했다. 기능 1은 앱이 질문한 뒤 답변을 녹음하고 전사하는 흐름이다. 기능 2는 탑승자가 시작한 세션에서 발화 구간을 짧게 받아 추억으로 남길 후보의 텍스트를 고르는 흐름이다. PC에서는 자연 대화 샘플을 전사하고 검수하는 도구를 구축했다.

검증 환경은 Pleos Connect v2.1.0 AVD, Android 14(API 34), Pleos SpeechToText SDK 3.3.1이다. 검증 앱 `com.drivediary.sttprobe`는 Android SDK Platform 37로 빌드한다. 초기 검증은 `9c30514`와 `4306726`에 기록되어 있고, 아래에는 이후의 통합 실험과 도구 구성도 포함했다. 실행 방법과 디렉터리 안내는 [Talk Rec README](../README.md)에 있다.

## 기능 1 · 질문과 답변 전사

- 앱에 질문을 표시하고 마이크 없는 PC에서도 실행할 수 있도록 합성 답변을 가상 입력으로 받았다. PCM을 앱 캐시에 저장한 뒤 다시 읽어 Pleos STT `Mode.ON_DEVICE`의 `sendAudio()`로 보냈다. 최종 콜백에서 ‘오늘 바다에 다녀왔어요’를 받았다.
- Pleos SDK의 `request()`는 SDK가 마이크를 사용하는 경로다. `sendAudio()`는 앱이 캡처한 PCM을 SDK에 넘기는 경로다. 가상 답변 실험은 질문 표시부터 저장·전사까지 검증했다. 앱의 `AudioRecord`에 물리 마이크 신호가 들어오는 경로는 아래 기능 2 실험에서 확인했다. [초기 실험과 실행 방법](../test/stt/README.md)

## 기능 2 · 마이크 입력에서 후보 텍스트까지

검증 앱은 화면에서 시작한 마이크 Foreground Service에서 `AudioRecord`로 16kHz 모노 PCM을 읽는다. 발화 감지(VAD)가 20ms 프레임을 검사하고 시작 직전 300ms를 포함해 RAM에 담는다. 1초 무음에서 발화를 닫으며 구간당 상한은 12초다. Pleos 온디바이스 STT에 구간별로 보내고 최종 전사에 경량 분류기를 적용한다. 처리 중 1건과 대기 1건으로 제한한다. 물리 마이크 시험에서는 PCM을 파일에 쓰지 않고 선택된 텍스트를 앱 캐시의 `live-story-candidates.txt`에 남긴다.

| 시험 | 조건과 결과 |
| --- | --- |
| 30초·120초 연속 합성 입력 | 30초 시험에서 최종 전사 3건을 받았다. 120초 시험은 발화 5건을 모두 전사했으며, 그중 3건은 차량 설정으로 화면을 전환한 뒤 처리했다. |
| 마이크 해제와 재개 | 6초 캡처 후 백그라운드에서 `AudioRecord`를 해제하고 약 10.1초 뒤 다시 열었다. 당시 입력은 무음이었다. 해제 구간에는 마이크 프레임이 들어오지 않는다. |
| 20분 RAM 통합 재생 | 앱 화면에서 합성 PCM을 20ms마다 직접 공급했다. 60,000프레임을 처리해 발화 80건 모두 최종 전사를 받았고, 오류와 대기열 누락은 0건이었다. 기대 후보 40건 중 27건을 저장했고 비후보 40건 중 오탐은 0건이었다. 발화 종료 감지부터 후보 판정까지 p95 1.72초, 앱 PSS 최대 54.8MiB였다. |
| 60초 물리 마이크 | 스피커에서 재생한 TTS를 USB 마이크로 받아 Pleos AVD에 전달했다. 차량 설정 화면으로 전환한 뒤 5건 모두 전사됐고 후보 3건을 저장했다. |
| 약 11분 물리 마이크 | 같은 스피커·USB 마이크 경로로 20분을 목표로 시작해 약 11분에서 종료했다. 차량 설정 화면에서 발화 22건의 최종 전사와 후보 11건을 확인했다. 관측한 STT 오류와 대기열 누락은 0건이었고, 시스템의 녹음 중 마이크 표시도 확인했다. |

Gleo 세션을 셸로 열었을 때 앱의 `isClientSilenced()`는 `false`였다. 당시에는 무음 입력이어서 실제 호출어 인식과 Gleo 청취 중의 마이크 배분은 확인하지 못했다. 현재 프로브는 앱 입력이 무음 처리되거나 오디오 경로가 바뀌면 부분 발화와 대기 입력을 폐기한다. [10초 갭과 Gleo 대조 시험](../test/stt/feature2.md) · [RAM 재생과 한영 혼용 실험](../test/stt/feature2-mixed.md)

## 후보 판정 모델과 평가 문장

- Pleos STT가 오디오를 텍스트로 변환하고, `TinyStoryModel`이 그 텍스트의 저장 후보 점수를 계산한다. 학습 48개, 임계값 선택 16개, 평가 42개로 나눈 실험에서 문자 2~4글자 조합을 입력으로 로지스틱 회귀를 학습했다. 전사 오류를 흉내 낸 변형을 포함한 84,229B 가중치를 검증 앱의 기본 모델로 사용한다.
- 한국어·한영 혼용·영어 합성 음성 12개를 `ko-KR`와 `en-US`로 각각 시험했다. `ko-KR` 전사에서 기대 후보 6건 중 4건을 찾았고 일반 대화 6건은 모두 제외했다. 외래어가 빠지거나 영어 문장이 의미를 잃는 사례가 있어, 최종 전사를 받았는지와 핵심 내용이 보존됐는지를 구분해서 본다.
- 다국어 MiniLM 고정 인코더와 선형 분류기를 비교했다. 직전 발화를 넣은 소규모 문맥 시험에서는 경량 모델과 MiniLM 모두 후보 검출이 늘었고, 오탐도 별도로 확인했다. AVD의 MiniLM 비교는 사전 토큰화한 입력에서 약 210MiB PSS와 288MiB RSS를 사용했다. 실제 마이크 프로브는 발화별로 판정하며 문맥 결합은 비교 실험 단계다.
- 기존 단문보다 실제 차 안 대화에 가까운 3~5턴 장면 24개를 작성했다. 한국어 12개, 한영 혼용 10개, 영어 2개로 나눴다. 같은 주제에 저장 후보와 제외 사례를 짝지어 문맥의 효과를 볼 수 있게 했다. [모델 비교 상세](../test/stt/feature2-mixed.md#모델-비교와-선택) · [차량 대화 평가 시나리오](../test/stt/story-dialogues.md)

## PC 대화 샘플 전사와 검수

- `yt-dlp`와 Deno로 한국어 음성 트랙을 받고 `faster-whisper`의 `large-v3-turbo`로 전사하는 Windows 환경을 구성했다. RTX 5060 Ti에서 CUDA FP16을 사용했다. 전체 파일이나 지정 구간을 전사하고 원본 시간 기준 JSON과 SRT를 생성한다. [PC 도구 설치와 실행](../dev-tools/README.md)
- 부부 대화 모음 영상에서 먼저 3구간, 총 4분 45초를 비교하고 이어 전체 약 45분을 전사했다. 전체 전사에서 972개 자막 구간을 만들었고, 추론은 약 78초 걸렸다. 유튜브 자동자막과 대조해 생일 일화, 중학교 만화 연재, 어린 시절 놀이, 대학 시절 자판기 커피 같은 후보를 찾았다. 짧은 맞장구나 외래어는 전사본에 따라 다르게 남아서 원음 검수 대상으로 분리했다. 영상은 라벨 기준을 잡는 파일럿으로 살펴봤으며 학습용 채택에는 재사용 허락 확인이 남아 있다. [검토한 영상](https://www.youtube.com/watch?v=hcn_hz3E1f0)
- 모델과 음성 원본, 전사 결과는 `dev-tools/.local/`에 보관한다. 검토한 영상의 전체 결과는 그 아래 `reviews/hcn_hz3E1f0-full.json`과 `reviews/hcn_hz3E1f0-full.srt`다.

## 디렉터리 정리와 검증 범위

`dev-tools`와 `test`를 `talk-rec` 아래로 옮겼다. 실행 안내는 저장소 기준 상대경로로 바꾸고, 기존 절대경로가 기록된 Python 가상환경은 같은 패키지 버전으로 재생성했다. 새 경로에서 `yt-dlp` 실행, RTX 5060 Ti의 CUDA 전사와 Android `assembleDebug` 빌드를 확인했다.

다음 검증은 동의받은 실제 대화로 백그라운드 20분과 목표인 2시간을 측정하는 것이다. 겹말·한영 혼용·주행 소음에서 핵심 내용이 남는지, 실제 Gleo 호출 시 앱의 입력이 유지되거나 차단되는지, 실차에서 시간당 오탐과 앱 메모리·CPU가 어느 수준인지 확인한다. 문맥 결합과 민감정보 제외는 제품 적용 전에 검증할 항목이다.
