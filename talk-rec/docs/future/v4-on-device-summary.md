# 미래 설계: 기기 안 요약·태그와 STT 견고성 (v4)

> **상태: 보류 (2026-11-13).** 지금은 팀 앱 연동을 먼저 하고, 연동 데모의 요약·태그는 외부 LLM으로 만든다([연동 설계](../app-integration/DESIGN.md)). 이 문서는 나중에 외부 LLM을 기기 안 처리로 바꿀 때의 설계다. 2026-11-13까지 논의한 내용을 [model-create/DESIGN.md](../../model-create/DESIGN.md) §13에서 옮겼다.

## 결정과 논의 기록 (2026-11-13)

- 요약 한 줄은 **좁은 일에 맞춰 학습한 소형 생성기**가 주 경로다. 템플릿 + 구절은 대비책이다(§4).
- **소리 모델은 계속 보류하고, 그 메모리 몫을 생성기에 쓴다.**
- 템플릿 기반만으로는 문장이 단조로워질 수 있다는 우려가 있어 생성기를 넣었다.
- 사용자는 **주행 중에도** 조금 지나서 녹음·요약·태그가 화면에 보이기를 원한다. 계산상 가능하다: 생성기는 저장한 묶음에만 돌고(시간당 많아야 7~10회), 묶음당 1~2초면 평균 CPU 1% 미만이다. 메모리는 M1 + 후보 E 약 80MiB, M1 + 후보 A 약 120~135MiB(추정). 확인할 것은 차량 CPU 지연, 생성 중 화면 끊김, **Pleos 주행 중 화면 규제**(운전자가 읽는 글을 띄울 수 있는지)다. 이 문서의 §4 "실행 시점"은 아직 "주행 뒤" 초안이며, 다시 꺼낼 때 주행 중 실행으로 고친다.
- STT 품질이 낮다고 저장 쪽으로 기울이지 않는다. "다시 들어볼 후보" 보관함도 만들지 않는다.
- Gleo AI는 쓰지 않는다. 앱이 글을 보내 생성을 받는 공개 API가 없다.
- Pleos STT는 신뢰도 점수를 넘겨주지 않는다(사용자 확인).

## 0. 왜 바꾸는가

- 사용자가 회상 화면에서 보는 것은 음성만이 아니라 **요약 한 줄과 태그**다. v3는 남길지만 정했다.
- 앱 안에서는 생성형 LLM을 쓸 수 없다. 한국어 한 줄 요약이 되는 가장 작은 범용 생성 모델(0.5B급 4비트)도 300~500MB가 필요해 앱 전체 400MB와 맞지 않는다. 외부 LLM은 쓰지 않고, Gleo AI는 앱이 글을 보내 생성을 받는 길이 없다(model-create/DESIGN.md §1).
- Pleos STT는 신뢰도 점수를 넘겨주지 않는다. STT 품질은 우리가 따로 어림해야 한다.
- 원칙: **M1의 남길 것/없음 판정을 지키면서** 기능을 더한다. 새 머리는 고정한 M1 몸통 위에 얹어, 판정이 바뀌는 일은 견고성 재학습 한 번뿐이게 한다.
- KoELECTRA(M1)는 인코더 전용이라 고르기·뽑기(분류, 구절 위치)만 하고 문장을 새로 쓰지 못한다. 자연스러운 한 줄은 별도의 소형 생성기가 맡는다(§4).
- **선행 점검 (T68)**: 생성기와 머리는 Gemini가 합성 장면에 단 제목·범주·구절을 따라 배운다. 그래서 Gemini가 **Pleos 전사만 보고** 주제·태그·한 줄을 제대로 뽑는지가 상한선이다. 이것을 실제 dev에서 먼저 확인한다. 남길 것/없음 판정(0.919)만 확인됐고 주제 추출은 확인되지 않았다.

## 1. 구조

```text
차량 신호 (NaviHelper 목적지·경로, FusedLocation, 시계, 날씨 가능 시) ─────────┐
                                                                               ▼
Pleos 줄 → ① 정규화 → ② 묶음 조립 → ③ 규칙 게이트 (기록 거부·명령·외부 소리, T56)
        → ④ M1 몸통 (고정, int8) ─┬─► keep 점수 / kind          ← 주 판정 (v3와 같은 역할)
                                  ├─► 템플릿 범주 머리 (새)       예: 추억, 아이의 하루, 계획, 놀이, 풍경
                                  ├─► 구절 고르기 머리 (새)       묶음 안 짧은 구절의 시작·끝 위치
                                  └─► 기록 거부 보조 머리 (새)
        → ⑤ 태그 조립 (규칙 = 일반 코드): 차량 신호 + 낱말 사전 (+ 템플릿 범주)
        → ⑦ 저장 구간 조립 → ⑧ 저장: 음성 + 자막 + 태그
주행이 끝난 뒤 (저장된 묶음만):
        → ⑥ 요약 한 줄: 소형 생성기 (주 경로, §4) → 지어내기 검사(규칙) → 통과하면 저장
             대비책: 범주의 템플릿 + 태그 + 구절 (규칙 = 일반 코드)
```

- **"규칙"은 학습하지 않는 일반 코드**다. 같은 입력에 항상 같은 결과를 내고 Kotlin으로 그대로 옮긴다. 학습하는 것은 ④의 머리들뿐이다.
- 머리는 M1 몸통의 출력(문장 표현, 토큰 표현)을 읽는 작은 층이다. 몸통은 고정하므로 keep 판정과 T58 내보내기 결과가 바뀌지 않는다. 머리만 따로 내보내 몸통 출력에 붙인다.
- ③ 게이트가 막은 묶음은 ④부터 돌지 않는다.

## 2. STT 견고성 (T54 → T64)

1. **측정 (T54)**: 실제 묶음 일부(20~30개)를 사람이 들으며 전사를 고친 기준 전사와 Pleos 글을 비교한다. 아이 말과 어른 말의 오류율, 짧은 대답 누락, 띄어쓰기, 줄이 끊기는 위치, 비슷한 소리로 바뀌는 낱말을 잰다.
2. **학습 (T64)**: 측정한 오류를 합성 글의 망가뜨리기에 반영하고, 같은 장면의 깨끗한 판과 망가진 판에 같은 판정을 내도록 하는 일관성 손실을 더해 M1을 **한 번** 다시 학습한다.
3. **관문 (T64)**: 다시 학습한 M1을 지금 M1(int8 + 0.957)과 같은 실제 dev에서 비교한다. 아래 중 하나라도 걸리면 **견고성 작업을 버리고 지금 M1을 그대로 쓴다.**
   - child+family dev 정답 수가 지금(31/37)보다 적다.
   - keep 재현율이 0.85 미만이다.
   - none 걸러 내기가 지금(7/12)보다 낮다.
   - 덧붙여 깨끗한 합성 글에서의 정확도 하락과, 사람이 고친 기준 전사와 Pleos 글 사이의 판정 차이를 함께 보고한다.
4. 관문을 통과한 몸통(또는 지금 몸통)을 고정한다. 이후 머리는 모두 이 몸통 위에서 학습한다.
5. **STT 품질 점수**: Pleos가 신뢰도를 주지 않으므로 묶음마다 (a) 음성 버퍼의 말소리 길이 대비 나온 글의 양, (b) 아주 짧은 줄의 비율, (c) 사전에 없는 낱말의 비율로 어림한다. **저장 판정에는 쓰지 않는다.** 구절 인용을 보일지 정하는 데만 쓴다.

## 3. 태그 (T65)

- **고정 목록 15~20개**(초안). 예: 가는 곳(할머니 댁·바다·놀이공원·학교), 사람(할머니·아빠·형제), 화제(음식·학교·놀이·자연·추억·계획), 때(주말·아침·저녁·계절).
- **출처 순서**: 차량 신호(목적지·목적지 종류·요일·시간대·휴게소 등 정차) → 낱말 사전(Pleos 글의 가족 호칭·장소·음식 등) → 템플릿 범주 머리. 차량 신호는 STT 품질과 상관없이 정확하므로 가장 앞에 둔다.
- 사전은 Pleos 오류를 고려해 띄어쓰기를 무시하고 짧은 변형을 허용한다(T56과 같은 정규화).
- M1 태그 머리는 넣지 않는다. 규칙 태그가 실제 dev에서 모자라다고 확인될 때만 나중에 검토한다.

## 4. 요약 한 줄 (T67 주 경로, T65·T66 대비책)

**주 경로: 좁은 일에 맞춰 학습한 소형 생성기 (T67)**

- "Pleos식으로 망가진 묶음 → 다이어리 한 줄" 한 가지 일만 학습한다. 범용 대화 모델이 아니다.
- 학습 자료: Gemini가 합성 장면 2,978개(모자라면 더 생성)에 한 줄 제목을 쓰고, 생성기가 이를 따라 배운다(증류). 제목은 장면에 있는 내용만 쓰게 지시한다.
- **후보 (2026-11-13 조사)**

  | 후보 | 구조 | 크기 | 장점 | 위험 |
  | --- | --- | --- | --- | --- |
  | **A** | KETI ke-t5-small(7,700만, Apache 2.0, safetensors)의 어휘를 64,128개 → 약 2만 개로 줄인 판 | int8 약 55MB (추정) | 공개 사전 학습을 이어받아 문장 품질 기대 | 어휘 축소 후 품질, SentencePiece 토크나이저의 Kotlin 이식 |
  | **E** | 고정 M1 몸통을 인코더로 쓰고 작은 디코더(2~4층)만 새로 학습 | 추가 10~20MB (추정) | 메모리 가장 적음, 토크나이저 하나 | 디코더를 처음부터 배워 자료가 1만 개 이상 필요할 수 있고 문장 품질이 낮을 수 있음 |

  제외: pko-t5-small(safetensors 없음, 라이선스 표기 충돌), KoBART base(int8로 약 124MB), mT5-small(safetensors 없음, 어휘 25만 개). 더 작은 한국어 생성 모델은 찾지 못했다.
- **지어내기 검사 (규칙)**: 생성한 문장의 사람·장소·사물 낱말이 묶음 글이나 태그에 없으면 그 문장을 버리고 대비책을 쓴다.
- **고르는 기준**: 실제 dev 남길 것 묶음 30개 안팎에서 A·E·대비책의 한 줄을 나란히 보여 사람이 더 나은 쪽을 고른다. 지어낸 내용은 30개 중 2개 이하(초안), int8 70MB 이하, 주행 뒤 처리로 감당할 지연. 기준을 넘는 후보 중 사람 선호가 가장 높은 것을 쓰고, 둘 다 못 넘으면 대비책만 쓴다.
- **실행 시점**: 주행 중에는 로드하지 않는다. 주행이 끝난 뒤(또는 정차 중) 그날 저장된 묶음에만 돌린다(초안). 그래서 M1과 동시에 메모리에 올라갈 필요가 없다.

**대비책: 템플릿 + 대화에서 뽑은 짧은 구절 (T65, T66)**

1. 템플릿 범주 머리가 범주를 고른다(추억, 아이의 하루, 계획, 놀이, 풍경 등 6~10개, 초안).
2. 구절 고르기 머리가 묶음 안에서 2~6어절 구절의 시작·끝을 고른다. 질의응답 모델과 같은 방식이다. 사전·품질 점수로 깨진 구절을 걸러 내고, 쓸 만한 구절이 없으면 쓰지 않는다.
3. 규칙이 범주의 템플릿(범주마다 여러 개, 전체 30~50개)을 고르고 빈칸을 태그와 구절로 채운다. 조사(와/과, 을/를) 맞춤, 빈칸 값이 없을 때 빈칸 없는 템플릿으로 바꾸기, 최근에 쓴 템플릿 반복 피하기를 규칙으로 한다.
4. 예: 범주 "추억", 태그 {가는 곳: 할머니 댁}, 구절 "조개 엄청 많이 주웠던" → "할머니 댁 가는 길, '조개 엄청 많이 주웠던' 이야기".
5. 생성기가 기준을 넘으면 템플릿 범주·구절 머리(T66)는 생성기의 지어내기 검사에서 떨어진 묶음에만 쓴다. 생성기가 기준을 넘지 못하면 이 대비책이 주 경로가 된다.

## 5. 기록 거부 보조 (T66)

- 규칙(T56)이 먼저다. 차단율이 합성 시험에서 73~79%로 95%에 못 미쳐(T56), 규칙이 놓친 변형을 M1 머리가 보조한다. 학습 자료는 T56 시험 묶음이다.
- **보조 머리만 반응했을 때는 그 묶음의 저장만 막고, 지난 저장을 소급해 지우지 않는다.** 소급 삭제는 규칙이나 화면의 "녹음하지 마" 버튼일 때만 한다.
- 화면 버튼이 가장 우선이다. 글로 거부를 잡는 것은 STT 오류 때문에 한계가 있다.
