# I9a — 고정 분류 1개 + 자유 키워드 최대 2개

작성일: 2026-11-13. 변경 범위는 `model-create/prompts/summary.md`, `model-create/tools/summary_relay.py`, `model-create/tests/test_summary_relay.py`와 이 문서다.

사용자가 제공한 리허설 관찰에서는 기존 고정 태그가 27건 중 22건에 `가족 이야기`를 붙였다. 그룹화에는 고정 분류를 사용하고 각 대화의 구별에는 구체적인 키워드를 사용하도록 계약을 바꿨다.

## 앱이 복사할 출력 계약

LLM 출력은 다음 네 필드를 가진 JSON 객체다. 아래는 유효한 JSON 예시이며 `kind`의 허용값은 `story`, `moment` 두 가지다.

```json
{"title":"비 오던 날 만두 가게 이야기","category":"추억","keywords":["만두","신발"],"kind":"story"}
```

형태: `{"title":"<=25자 제목","category":"목록 중 하나","keywords":["0~2개"],"kind":"story" 또는 "moment"}`. `keywords`의 원소는 설명 문구가 아니라 실제 키워드이며 빈 배열도 허용한다.

릴레이의 `POST /summarize` 요청 형식은 기존과 같다.

```json
{"transcript":"지어낸 대화 내용","model":"gemini-3.8-flash-medium"}
```

성공 응답은 정확히 다음 일곱 필드다. `elapsed_ms`는 요청 처리 시간인 0 이상의 정수이며 아래 값은 형식 설명용이다.

```json
{"title":"비 오던 날 만두 가게 이야기","category":"추억","keywords":["만두","신발"],"tags":["추억","만두","신발"],"kind":"story","model":"gemini-3.8-flash-medium","elapsed_ms":1234}
```

- 앱의 분류·필터 값은 `category`, 구체적인 표시어는 `keywords`를 사용한다.
- 구형 클라이언트 호환 필드 `tags`는 항상 `[category] + keywords` 순서다. 키워드가 없으면 `[category]`다. LLM이 추가로 보낸 `tags`가 있어도 무시하고 릴레이에서 다시 만든다.
- `tags`의 두 번째·세 번째 원소는 자유 키워드이므로 전체 원소를 고정 분류 enum으로 검사하지 않는다.
- `category`, `keywords`는 필수다. 예전 `{title, tags, kind}` 형식만 보내는 LLM 출력은 실패한다. 추가 LLM 필드는 무시하고 응답에는 위 일곱 필드만 보낸다.

## 분류 목록 — 정확히 하나

추억, 아이의 하루, 학교, 놀이, 음식, 자연·풍경, 여행 계획, 가족 이야기, 친구 이야기, 운전·길, 노래·웃음, 동물, 계절

총 13개다. `가족 이야기`는 가족 구성원이나 가족 행사에 관한 이야기일 때만 선택한다. 가족이 화자라는 이유로 선택하거나 기본값으로 쓰지 않는다. 친구 관계·함께 한 경험은 `친구 이야기`, 운전·길 안내는 `운전·길`로 표현할 수 있다.

릴레이는 프롬프트의 `## 분류`부터 다음 `##` 제목 전까지에서 쉼표가 들어간 유일한 줄을 읽는다. 목록은 한 줄로 유지하고 이 섹션의 다른 설명에는 쉼표를 추가하지 않는다. 각 항목의 앞뒤 공백을 제거하고 빈 항목이나 중복 항목이 있으면 시작에 실패한다. 코드 안에 별도 분류 목록을 두지 않는다.

## 검증 규칙

앱과 릴레이가 공유할 구조 검증은 다음과 같다.

| 필드 | 규칙 |
| --- | --- |
| `title` | 문자열, 원문 길이 1~25 Unicode 코드 포인트, 공백만으로 구성되지 않음, CR/LF 없음, 올바른 UTF-8로 표현 가능. 자동 trim하지 않음. 기존 검증 그대로 유지. |
| `category` | 문자열이며 위 13개 중 하나와 정확히 일치. 자동 trim이나 유사어 치환 없음. |
| `keywords` | 필수 배열, 원소 수 0~2개. 각 원소는 문자열. 아래 정규화·검증을 모두 통과해야 함. |
| `kind` | 문자열 `story` 또는 `moment`. |

키워드 처리 순서는 다음과 같다.

1. 각 문자열의 앞뒤 공백을 `strip()`으로 제거한다. 바깥쪽 공백·탭·줄바꿈은 제거하지만 내부 공백은 제거하지 않는다.
2. 문자열 전체가 `[가-힣A-Za-z0-9·]{1,6}`에 일치해야 한다. 한글 완성형 U+AC00~U+D7A3, ASCII 영문, ASCII 숫자, 가운데점 U+00B7만 허용한다. 내부 공백, 다른 구두점, 이모지, 한자, 분리 자모는 허용하지 않는다.
3. 숫자만으로 구성된 문자열을 거부한다. 예: `123` 불가, `RC카`, `ABC123` 가능.
4. 어느 분류와든 같은 문자열을 거부한다. 현재 선택한 분류만 비교하는 것이 아니다.
5. trim 후 영문 대소문자를 무시한 중복을 거부한다. 릴레이는 `casefold()`를 사용하며 허용 영문 범위에서는 소문자 비교와 같다. `ABC`, `abc`는 중복이다.
6. 통과한 순서와 영문 대소문자를 보존해 `keywords`에 반환한다. 개수 초과나 잘못된 원소를 자동 삭제하지 않는다.

예: `[]` 허용, `[" 만두 ", "RC카"]` → `["만두", "RC카"]`, `["두 단어"]`, `["가나다라마바사"]`, `["123"]`, `["추억"]`, `["ABC", "abc"]`, 세 원소 배열은 거부한다.

내용 선택 규칙은 프롬프트에 명시한다. 실제로 언급한 사물·활동·음식·동물·행사 등의 짧은 명사만 고른다. 사람 이름·별명·장소명·가게명·학교명·브랜드명 및 건강·금액·갈등 같은 민감한 내용은 키워드에서 제외한다. STT 오류나 불분명한 낱말은 추측해 보정하지 않는다. 확실한 구체어가 없으면 `[]`를 쓴다. 이 의미 판단은 LLM에 지시하며 릴레이의 문자·스키마 검증만으로 이름이나 민감정보 여부를 판별하지는 않는다.

제목 프롬프트 규칙도 기존과 같다. 25자 이하의 담백한 장면 요약으로 마침표 없이 끝내고 대화에 없는 장소·감정·사건, 사람 이름, STT 추측 보정을 쓰지 않는다. 호칭은 허용한다. 이러한 내용·문체 규칙은 위 구조 검증과 구별한다.

출력 바깥 공백과 전체를 감싼 JSON/일반 코드 펜스는 기존처럼 제거한다. JSON·스키마·키워드 검증 실패 시 같은 입력으로 한 번 더 요청하고 두 번째도 실패하면 HTTP 502 `{"error":"invalid_output"}`를 반환한다. 백엔드 오류는 502 `backend_error`, 사용량 제한은 429 `usage_limit`이며 이 오류 자체를 재시도하지 않는 기존 동작을 유지한다.

## 프롬프트 변경 요약

- `## 태그`의 고정 태그 1~3개를 `## 분류`의 고정 분류 1개와 `## 키워드`의 자유 키워드 0~2개로 바꿨다.
- 분류에 `친구 이야기`, `운전·길`을 추가하고 `가족 이야기`의 선택 조건을 명시했다. 도입부도 가족·친구를 포함하는 차 안 대화로 표현했다.
- 출력 예시를 `{title, category, keywords, kind}`로 바꿨다. 지어낸 예시는 만두·신발에 관한 추억, 탁구·라켓에 관한 친구 이야기, 키워드 없는 웃음 장면의 세 개다.
- `## 제목`과 `## 종류`의 규칙은 유지했다. 프롬프트는 BOM 없는 UTF-8, LF로 저장했다.

## 남은 질문

- 앱 작업에서 `category`, `keywords`를 분리해 저장·표시·필터링할지, 과거 `tags` 레코드를 어떻게 읽을지 정해야 한다. 이 작업은 호환 응답까지만 변경했다.
- 여러 분류가 겹치는 대화에서 중심 주제를 선택하는 일관성과 저품질 STT의 의미 오류는 별도 품질 평가가 필요하다. 가상 대화 5건만으로 실제 분류 분포 개선을 판단할 수 없다.
- 이름·브랜드·민감한 내용의 의미 검사는 프롬프트에 의존한다. 앱에서 별도 검사가 필요한지는 후속 작업에서 정한다.

실제 전사와 `.local/real/**`는 읽거나 변경하지 않았다. 커밋·푸시·브랜치 전환을 하지 않았다.
