# 남길 대화 묶음 판정 모델 설계 (v3)

차 안 대화를 묶음 단위로 보고 **"이 묶음을 남길 것인가"**를 판정하는 온디바이스 모델의 설계다. **2026-11-13부터 팀 앱 연동이 먼저다**([연동 설계](../docs/app-integration/DESIGN.md)). 연동 데모의 요약·태그는 외부 LLM으로 만들고, 기기 안 요약·태그와 STT 견고성(v4)은 [미래 설계](../docs/future/v4-on-device-summary.md)로 옮겼다. 남기기로 한 묶음은 음성과 자막으로 저장한다. v3는 2026-11-11 데모(T40~T47)에서 측정한 결과로 v2를 고친 것이다. **추정**이나 **초안**이라고 적은 수치는 측정으로 대체해야 한다. 작업별 기록은 [docs/model-create](../docs/model-create/)에, 라벨 기준은 [rubric.md](rubric.md)에, 작업 단위는 [TASKS.md](TASKS.md)에 있다.

**두 모델 구성 (2026-11-12 정리)**: 앱에 들어갈 모델은 둘이다. **대화 모델**은 Pleos STT 글로 묶음을 "남길 것 / 없음"으로 판정하는 주 모델이고, 이 문서 대부분이 이 모델의 설계다. **소리 모델**은 같은 마이크 음성에서 웃음·고함·울음을 잡는 보조 모델로, 지금은 **보류**다. 앱에는 대화 모델을 먼저 넣고, 소리 모델은 나중에 끼울 자리만 둔다(§5, §6.2). 두 모델은 아직 PC에서 따로 시험만 했고 앱 안에서 함께 돌린 적은 없다.

## 0. v2에서 바뀐 것과 이유

| | v2 | v3 | 바꾼 근거 (§2) |
| --- | --- | --- | --- |
| 모델의 주 판정 | `keep` 0·1·2 + 태그 8종 + 제외 사유 | **남길 것 / 없음** 이진. 이야기·한 줄 순간 구분은 참고 출력 | 사람도 LLM도 이야기↔한 줄 순간에서만 흔들린다 |
| 학습 데이터 | 유튜브 영상 + LLM silver 라벨 | **합성 대화**(라벨이 만들 때 정해짐) | 편집 안 된 차 안 영상이 드물고, LLM 라벨이 사람과 16/35만 일치 |
| 실제 영상의 역할 | 학습 주력 | **흐름 참고 + 평가 전용** | 위와 같음 |
| 학습 글의 모습 | Whisper 전사 + 오류 증강 | **Pleos STT가 내놓는 글 모양**으로 망가뜨린 합성 글 | 앱 입력은 Pleos 글이고 Whisper와 모양이 다르다 |
| 모델 입력 | 글 + 숫자 단서 5개 | **글만** | 모양 단서는 실제 묶음에서 신호가 없다 |
| 묶음 닫기 | 침묵 20초 / 90초 / 12턴 | **침묵 20초 / 90초** (턴 수 조건 삭제, 초안) | Pleos는 한 묶음에 줄을 20개 안팎 낸다 |
| 평가 | 승인 영상의 Whisper 전사 | **실제 음성 → Pleos 전사 → 사람이 듣고 판정** | 최종 입력과 같은 조건이어야 한다 |

v2에서 그대로 가져가는 것: 결과물은 음성 구간 + 자막이라는 방향, 묶음이 닫힌 뒤 판정하는 늦은 판정, 사람 승인 관문, 저장 상한, 수집기·묶음 생성기·검토 콘솔. v2의 `keep` 0·1·2 라벨, 태그 8종, 숫자 단서, silver 라벨러 주력 계획은 쓰지 않는다.

## 1. 목표와 범위

- **목표**: 주행 중 Pleos STT가 내놓는 글을 묶음으로 모아 "남길 것 / 없음"을 판정한다. 남길 묶음의 음성을 파일로 저장하고 자막을 붙인다.
- **모델의 역할**: 추억의 가치를 최종 판단하지 않는다. "대화가 형성됐거나 남길 한마디가 있었다"는 후보를 걸러 낸다. 최종 확인은 사용자가 한다.
- **두 모델의 역할**: 대화 모델이 저장 후보를 고른다. 소리 모델은 넣게 되면 후보로 고른 묶음에 울음·고함이 있으면 저장을 취소하는 확인 단계로만 쓴다. 소리로 점수를 올리는 방식은 근거가 없어 쓰지 않는다(§2).
- **제약**: 앱 전체 RAM 400MB 이하, CPU 3% 이하 권고. Pleos STT는 플랫폼 기능이라 우리 앱 프로세스 밖에서 돈다. 그래서 이 예산에 드는 것은 우리 앱이 하는 일(두 모델, 묶음 조립, 음성 버퍼, 저장)이다. 심사가 앱 프로세스만 재는지는 공모전 안내로 확인해야 한다. [Pleos 성능 기준](https://document.pleos.ai/en/docs/pleos-only/vehicle-app-developer-guide/app-runtime-environment-resources-guide/app-performance-platform-identify)
- **저장 상한**: 주행 1시간당 최대 10분. 넘으면 점수가 높은 묶음을 남긴다.
- **대상 탑승 구성 (2026-11-12 결정)**: 지금은 **아이(아기~초등) + 가족**이 함께 탄 대화에 맞춘다. 음성 추억은 아이 어릴 때를 돌아보는 쓰임이 크다. 어른끼리(친구·부부·어른 가족)의 대화는 수다·뒷얘기가 많아 사람끼리도 남길지 판단이 갈린다(T50 판정에서 사람↔Claude 불일치 3건이 모두 어른만 있는 묶음). 친구·동료처럼 가족이 아닌 사람끼리의 대화는 남기지 않는다(`none`, [rubric §2](rubric.md)). 부부와 어른 가족 묶음은 판정은 하되 참고로만 둔다.
- **범위 밖**: 질문·대화거리 추천, 사용자 피드백 개인화. 요약 한 줄과 태그는 연동 데모에서 외부 LLM으로 만들고([연동 설계](../docs/app-integration/DESIGN.md)), 기기 안 처리는 [미래 설계](../docs/future/v4-on-device-summary.md)다. 대화 모델(M1)의 판정은 계속 기기 안에서 한다. Gleo AI는 쓰지 않는다: 공개된 연동은 Gleo가 사용자 음성 명령으로 앱 기능을 부르는 방향뿐이고, 앱이 글을 보내 생성 결과를 받는 API는 없다(2026-11-13 조사, [Gleo Interface](https://document.pleos.ai/en/docs/pleos-only/app-integration-guide/guide/core-concepts)).

## 2. 데모에서 확인된 사실

모두 2026-11-11 측정이다. 실제 묶음 표본이 20~25개뿐이라 비율은 방향만 본다.

| 확인된 것 | 수치 | 설계에 주는 의미 |
| --- | --- | --- |
| Pleos STT(ON_DEVICE, `sendAudio`)는 여러 사람이 섞인 실제 차 안 음성을 받아 적는다 | 25클립 오류 0, 빈 결과 0 (T44) | 입력 경로는 성립한다 |
| Pleos 글은 Whisper와 모양이 다르다 | 클립당 줄 수 중앙값 21, 줄당 글자 중앙값 13·p90 35·최대 85, 반복 환각 0건 (Whisper 계열 22건) (T45) | 학습 글을 Pleos 모양으로 만든다 |
| Pleos 글의 품질은 Whisper보다 낮다 | 눈가림 비교 25개 중 Pleos 선택 2, large-v3 긴 문맥+힌트 9 (T42) | PC 쪽 기준 전사는 large-v3 긴 문맥+힌트 |
| 품질이 낮아도 Pleos 글로 판정이 된다 | Gemini가 글만 보고 남길 것/없음 17/20, 세 라벨 13/20. Whisper 글은 13~15/20 | 접근을 유지한다 |
| 글 내용 없이 모양만으로는 갈리지 않는다 | 줄 수·길이·간격으로 12/20 (전부 한쪽으로 찍으면 12~13/20). 실제 이야기와 없음은 둘 다 평균 약 75초·20줄 | 숫자 단서를 입력에서 뺀다 |
| 이야기↔한 줄 순간 경계가 불안정하다 | Gemini가 한 줄 순간 5개 중 0개 맞힘. 합성 훑어보기의 불일치 4건 전부 이 경계 | 주 판정을 이진으로 둔다 |
| 음향 태그(웃음·노래·화자 수)를 붙여도 LLM 판정이 나아지지 않는다 | 글만 16/35, 음향 태그 추가 16/35 (T41) | 음향 단서는 보류 |
| 큰 음향 모델은 따로 녹음된 웃음·비명·울음을 차 안 소리 위에서도 구분한다 | AST(346MB): 세 가지 구분 정확도 깨끗할 때 92%, 차 안 소리가 더 클 때(−5dB) 84%. 웃음↔비명 혼동 7% 이하, 울음을 웃음으로 8~15% (T48) | 소리 확인 단계는 기술적으로 가능하다 |
| 그러나 실제 클립에서는 웃음·노래 점수가 사람 판정과 무관하다 | 한 줄 순간 대 나머지 AUROC 0.49~0.52 (35클립) | 소리로 점수를 올리는 방식은 근거가 없다. 보류 |
| 작은 음향 모델(EfficientAT mn10, 19.5MB)은 큰 모델과 같은 수준으로 웃음·비명·울음을 구분한다 | 10초에 CPU 47ms. 세 가지 구분 94%(깨끗) / 84%(−5dB), 웃음–비명 AUROC 0.985 이상. 다만 숨·기침·하품 오경보가 AST보다 높고(최대 36%), 하품의 44%를 울음으로 잡는다. 실제 클립 AUROC 약 0.5. mn04(3.9MB)는 더 약함 (T48b) | 크기는 문제가 아니다. 사건 아닌 소리의 오경보와 실제 장면 근거 부족이 문제다 |
| 제목·지표로 사전 선별한 유튜브 영상은 대부분 쓸 수 없다 | 16묶음 중 없음 12, "차 안 아님" 코멘트 6 | 실제 영상은 사람 승인 필수 |
| 합성 대화는 본보기 장면을 주면 사람 눈에 실제 같다 | 33개 중 실제 같음 29, 의도 라벨과 일치 29 (T45) | 합성을 학습 주력으로 쓴다 |
| 합성 데이터에 지름길이 생기기 쉽다 | 없음을 짧게 만든 묶음: 모양만으로 84% 맞음 → 학습한 모델이 실제 없음 8개 중 0~1개만 맞힘. 길이를 겹치게 고친 뒤 모양 61%, 실제 없음 2~4개 맞힘 (T46, T47) | 지름길 검사를 관문으로 둔다 |
| 합성 평가 점수는 실제 성능이 아니다 | 합성 평가 91~100%, 실제 68~75% | 수치는 실제 Pleos 묶음으로만 말한다 |
| 큰 인코더의 이점이 보이지 않는다 | 실제 20묶음: 글자 n-gram 75%, KoELECTRA-small 73%, mmBERT-small 73%, roberta-small 68%, Gemini 85% | 후보를 n-gram과 KoELECTRA-small로 좁힌다 |
| 크기와 속도 (PC CPU 1스레드, fp32) | n-gram 1MB·1ms, KoELECTRA-small 56MB·65ms, roberta-small 272MB·214ms, mmBERT-small 219MB·279ms | 200MB급은 제외 |

**주행 중 STT (2026-11-11, 별도 세션의 AVD 시험)**: 정차 중 시작한 녹음 세션이 차량 설정 화면으로 전환하고 주행 규제(D단·30km/h)가 켜진 뒤에도 마이크 PCM을 받아 Pleos STT로 전사했다(최종 전사 1/1, 1/1, 2/2, 60초 세션). 이 시험에서 앱이 마이크 PCM을 직접 받아 `sendAudio`로 넘겼으므로, 소리 모델에 쓸 음성도 앱 안에 이미 있다.

**확인하지 못한 것**: 실제 차량 마이크로 들어온 소리의 전사 품질, STT를 수십 분 이어 받을 때의 끊김과 누락, 마이크 원본의 파일 저장과 재생, 양산 차량에서의 동작, 두 모델을 함께 돌릴 때의 앱 메모리·CPU. 데모는 에뮬레이터에 영상 음성 파일을 넣은 것이다. 이 항목들은 모델 통합 뒤에 다시 확인한다(T57, T60, T61).

## 3. 문제 정의

**줄**은 Pleos STT가 확정해 내놓는 결과 하나다. **묶음**은 이어지는 줄들의 구간이고, 판정 단위다.

**묶음을 닫는 조건(초안)**: 줄 사이 침묵 20초, 또는 길이 90초 중 먼저 오는 것. 실제 Pleos 출력의 줄 시각으로 다시 확정한다.

```text
입력:  [CLS] 줄1 [SEP] 줄2 [SEP] … [SEP]      (n-gram 모델은 줄을 줄바꿈으로 이은 글)
       · 화자 표시 없음, 문장부호 없음, 학습과 같은 정규화
       · 최대 256토큰(초안). 넘치면 앞 절반과 뒤 절반을 남긴다
출력:  keep 점수(0~1) + 참고 출력 kind(이야기 / 한 줄 순간)
```

- **늦은 판정**: 묶음이 닫힌 뒤 판정한다. 저장은 말이 끝나고 최대 1~2분 뒤에 일어난다.
- **저장 구간 조립**은 모델 밖 규칙이다. keep 점수가 문턱값 이상인 묶음을 고르고, 연달아 통과한 묶음은 합치고, 앞 3초·뒤 2초 여유를 둔다(초안). 시간당 상한에 닿으면 점수가 낮은 것부터 밀어낸다.
- **정책 차단**(기록 거부, 기기 명령, 라디오·통화 소리)은 규칙으로 먼저 처리한다(§5). 데모에서 다루지 않았으므로 설계만 유지한다.

## 4. 라벨 체계

기준과 경계 사례는 [rubric.md](rubric.md)에 있다.

| 필드 | 값 | 용도 |
| --- | --- | --- |
| `keep` | `keep` 남길 것 / `none` 없음 | **주 판정** |
| `kind` | `story` 이야기 / `moment` 한 줄 순간 (`keep`일 때만) | 참고. 회상 화면의 표시와 분석에만 쓴다 |
| `unsure` | 참/거짓 (사람 라벨에만) | 판단이 갈리는 묶음. 평가에서 따로 센다 |
| `policy` | `optout` 기록 거부 / `command` 기기 명령 / `external` 라디오·내비·통화·영상 소리 | 저장 차단. 규칙이 주, 모델은 보조 |

- **부정적인 대화는 `none`이다.** 다툼, 혼내기, 떼쓰기, 험담, 안 좋은 소식은 이야기가 형성됐더라도 남기지 않는다. 다시 보고 싶어 할 사람이 없기 때문이다. 기준은 소재가 아니라 지금 차 안의 분위기다. 장난스러운 놀림과, 속상했던 일을 따뜻하게 들려주는 대화는 남긴다.
- 묶음 안 어디든 이야기나 한 줄 순간이 있으면 `keep`이다. 저장 단위가 묶음 전체이기 때문이다(초안, §12).
- 합성 데이터의 라벨은 카드가 정한다. 사람은 표본을 훑어 그 라벨이 말이 되는지만 확인한다.
- 실제 묶음의 라벨은 사람이 **음성을 듣고** 단다. 사람 판정이 곧 평가의 정답이므로 두 사람이 따로 달아 일치도를 잰다.

## 5. 온디바이스 구조

```text
AudioRecord ─┬─► PCM 순환 버퍼(최근 3분, RAM) ─────────────────────────┐
             └─► Pleos STT(sendAudio, ko-KR, ON_DEVICE, 앱 밖) ─► 확정 줄 + 시각
                        → ① 정규화          학습과 같은 함수               │
                        → ② 묶음 조립        침묵·길이로 닫음               │
                        → ③ 규칙 게이트      호출어·명령·기록 거부 패턴, 미디어 재생 상태
                        → ④ 대화 모델        묶음당 1회 → keep 점수, kind  │
                        → ④b 소리 모델(보류) keep 후보 묶음만, 버퍼 음성 ◄─┘
                                            10초 창 → 울음·고함이면 저장 취소
                        → ⑤ 저장 구간 조립   병합, 앞뒤 여유, 상한 관리, 소급 삭제
                        → ⑥ 저장            버퍼에서 잘라 압축 음성 + 자막 + 시각
```

- **PCM 순환 버퍼**는 16kHz 모노 16비트로 3분에 약 6MB다. 묶음 최대 길이 + 판정 대기 + 여유보다 길어야 한다. 저장과 소리 모델이 같은 버퍼를 쓴다.
- **④b 소리 모델 자리**: 처음 통합에서는 인터페이스만 두고 "취소 안 함"으로 동작한다. 넣게 되면 대화 모델이 남길 것으로 고른 묶음에만 돌린다. 묶음 음성을 10초 창으로 나누고, 10초보다 짧은 창은 무음으로 10초까지 채운다(T48: 짧은 입력은 점수가 포화한다).
- **기록 거부**는 그 묶음과 직전에 저장한 구간까지 소급해 지운다.
- **세션 종료·마이크 중단** 시 버퍼와 열린 묶음을 지운다.
- **대화 모델 로드 실패·메모리 압박 시**: M0(n-gram)는 실제에서 전부 남김과 같은 수준이라(T55) 대비책으로 싣지 않는다. 대신 규칙 게이트를 통과한 묶음을 모두 저장 후보로 보고 시간당 상한으로만 거른다(2026-11-13, 초안).
- 팀 앱 안에서의 구조(상시 녹음 서비스, 저장, 외부 LLM 요약·태그)는 [연동 설계](../docs/app-integration/DESIGN.md)에 있다.

**넣는 조건(초안)**: 사람이 승인한 실제 차 안 음성에서 울음·고함 장면을 모아 다시 시험해, 정상 남길 것 묶음을 잘못 취소하는 비율이 5% 이하이고 부정 묶음을 취소하는 효과가 보일 때만 넣는다. 그 전까지 ④b는 비워 둔다.

## 8. 데이터 설계

### 세 가지 데이터와 역할

| 데이터 | 만드는 법 | 쓰는 곳 | 라벨의 출처 |
| --- | --- | --- | --- |
| **합성 묶음** | 장면 카드 → LLM이 대화 작성 → Pleos 모양으로 망가뜨림 | 학습, 합성 내부 점검 | 카드가 정함 |
| **실제 평가 묶음** | 실제 차 안 음성 → Pleos STT → 묶음 | dev(모델·문턱값 선택), test(최종 보고) | 사람이 듣고 판정 (2인) |
| **흐름 참고 영상** | 사람이 승인한 무편집 차 안 영상 | 본보기 장면을 쓸 때 참고, 합성 분포 점검 | — |

실제 영상의 음성·전사는 `.local/`에만 두고 학습 글로 쓰지 않는다. 본보기 장면은 전부 새로 지어낸다.

### 합성 묶음 만들기 (T43, T45, T47에서 구현)

1. **카드**: 라벨(이야기 40 / 한 줄 순간 20 / 없음 40), 흐름 유형, 가족 구성, 상황, 화제, 끼어드는 요소, 목표 줄 수와 길이, 경계 사례 여부를 정한다. **라벨별 길이·줄 수·가족 구성 분포를 겹치게 한다.**
2. **대화 작성**: agy의 Gemini 3.8 Flash(medium)가 카드 4장씩 받아 화자·시각이 붙은 장면을 쓴다. 배치마다 본보기 장면 2~3개를 넣는다. 본보기는 `prompts/synth-examples/`에 28개가 있다.
3. **형식 검사**: 줄 수 ±40%, 길이 ±50%, 화자, 시각, 본보기·기존 장면과의 유사도. 실패한 장만 다시 요청한다.
4. **망가뜨리기**: Pleos 오류 프로파일(T45)에 맞춰 화자와 문장부호를 지우고, 짧은 줄로 쪼개고, 아이 화자의 낱말을 바꾸고, 겹친 말과 짧은 대답을 일부 지운다. 반복 환각은 넣지 않는다.
5. **지름길 검사(관문)**: 아래 중 하나라도 걸리면 그 데이터로 학습하지 않는다.
   - 모양 특징만으로 남길 것/없음을 맞히는 정확도가 다수 클래스 비율 + 10%p를 넘는다.
   - 글자 n-gram이 합성 평가에서 거의 다 맞히는데 실제 dev에서는 크게 떨어진다(초안: 차이 15%p 초과). 합성 "없음"의 내용이 단조롭다는 신호다.
6. **사람 훑어보기**: 새 카드 설계나 지시문을 쓸 때마다 30~60장을 본다. 실제 같음 85% 이상, 의도 라벨과 일치 85% 이상이어야 한다.

**부정적인 대화**: 카드에 "여러 번 주고받지만 분위기가 부정적이라 `none`"인 유형(다툼, 혼내기, 떼쓰기, 험담, 걱정스러운 소식)을 넣고, 같은 소재의 밝은 판(`keep`)과 짝지어 만든다. 지금까지 만든 합성 묶음에는 이 유형이 없으므로 다시 만들어야 한다(T53).

**알려진 한계**: 부정적인 분위기는 글만으로 가리기 어려울 수 있다(언성과 울음은 글에 없다). 합성 "없음"의 내용이 실제보다 단조롭다(n-gram이 합성에서 98%, 실제에서 75%). 아이 말 오류와 짧은 대답 누락 비율은 표본이 부족해 어림값이다.

### 실제 평가 묶음 만들기

1. **음성 확보**: 사람이 승인한 무편집 차 안 영상. 직접 녹음은 하지 않기로 했다(§12). 영상은 카메라·휴대폰 마이크로 녹음돼 차량 마이크와 다르다는 한계가 있다.
2. **Pleos 전사**: 음성을 16kHz 모노 PCM으로 바꿔 에뮬레이터의 Pleos STT에 넣는다(T44 경로).
3. **묶음**: Pleos 줄의 시각으로 §3 조건에 따라 묶는다.
4. **사람 판정**: 청취 화면에서 음성을 듣고 `keep`·`kind`·`unsure`를 단다. 두 사람이 따로 단다.
5. **분할**: 출처(영상·주행) 단위로 dev와 test를 나눈다. **test는 최종 보고 때만 본다.** 합성 데이터를 고칠 때 보는 것은 dev뿐이다.

**규모(초안)**: 아이 + 가족 묶음 기준 **8가족 이상에서 100묶음 이상**(dev 약 60, test 약 40, 음성 약 2.5시간). 2026-11-12 현재 승인 영상 13개, 묶음 76개(dev 55, test 21)를 모두 판정했지만, 그중 아이 + 가족 dev 묶음은 약 24개이고 대부분 두 가족이다. 출처마다 탑승 구성(아이+가족 / 어른 가족 / 부부 / 친구)을 표시하고 주 수치는 아이+가족 묶음에서 낸다. 어른만 있는 묶음은 참고로 둔다. 같은 채널(같은 가족)의 영상은 dev와 test에 나뉘지 않게 한다.

**판정 분담 (T50d)**: test 묶음은 사람이 제안 없이 듣고 판정한다. dev 묶음은 Claude가 전사 글로 먼저 판정하고 사람이 확인·수정한다. 사람이 제안을 보고 고르므로 dev의 사람↔Claude 일치도(κ 0.93)는 높게 나오는 쪽으로 치우쳐 있다.

### 큰 모델을 쓰는 곳

- **기준선**: Gemini가 실제 Pleos 글을 판정한 결과를 평가표에 함께 둔다.
- **보조 경로(보류)**: 승인된 실제 음성이 많이 모이면, Gemini가 Pleos 글에 단 라벨로 작은 모델을 추가 학습시키는 방법을 시험한다. 합성만으로 실제와의 차이가 줄지 않을 때 쓴다.

## 9. 학습 설계

1. **목표**: `keep` 이진 BCE가 주, `kind` 3분류가 보조 손실(가중 0.2)이다.
2. **입력**: §3. 숫자 단서는 넣지 않는다.
3. **분할**: 합성은 장면(카드) 단위로 train/val을 나눈다. val은 학습이 도는지 보는 용도일 뿐이다.
4. **문턱값**: 실제 dev에서 "남길 것 재현율"과 "시간당 저장 분량"으로 정한다.
5. **비교**: M0 대 M1, 합성 규모(400·1,000·3,000·10,000장) 학습 곡선. 시드 3개 평균과 실제 묶음 재표집 구간으로 말한다.
6. **내보내기**: M1을 고르면 dev에서 보정 후 ONNX int8로 내보낸다. M0는 가중치 표로 내보낸다.

| 정책 | 기록 거부·기기 명령 묶음이 저장되지 않는 비율 | 0.95 이상 (규칙 병행) |
| 소리 모델 (넣을 때) | 정상 남길 것 묶음을 잘못 취소하는 비율 | 0.05 이하, 실제 차 안 음성에서 |
| 기기 | 두 모델을 함께 돌린 증분 PSS, p95 지연, 평균 CPU, 20분 soak, 저장 파일 재생 | §7 목표 |

## 11. 진행 순서

| 단계 | 내용 | 끝났다고 보는 조건 |
| --- | --- | --- |
| **P0 실제 평가 묶음** | 영상 승인, Pleos 전사, 청취 판정 | 아이+가족 8가족 이상, 100묶음 이상(§8), 사람 간 κ 0.6 이상 |
| P1 라벨 기준 확정 | 루브릭 v3 경계 사례 보강, 라벨 정책 결정(§12) | 사람 간 불일치 묶음을 보고 기준을 고침 |
| P2 합성 대량 생성 | 카드 다양화, 지름길 검사, 훑어보기 | 3,000장 이상이 관문 통과 |
| P3 학습과 선택 | M0·M1, 학습 곡선 | §10 기준을 실제 dev에서 통과하는 모델 1개 |
| P4 기기 음성 저장 | 순환 버퍼, 파일 저장과 재생 | AVD에서 마이크 원본이 파일로 남고 재생됨, CPU·PSS 수치 |
| P5 기기 추론 | 대화 모델 내보내기, 토크나이저·정규화 이식, AVD 측정. 소리 모델 자리(④b) 인터페이스 | §7 목표 통과, Python↔기기 점수 일치 |
| P6 통합 | 판정·저장·소급 삭제·상한 관리, 20분 soak. 통합 뒤 연속 STT 수신 재확인 | 누락·오류 0 |
| P7 최종 테스트 | test 묶음으로 최종 수치 | 주 지표 보고 |
| (보류) 소리 모델 | 실제 차 안 울음·고함 음성으로 재시험, 넣으면 ④b에 연결 | §6.2 넣는 조건 |

P0가 가장 먼저다. P4는 모델과 무관하므로 병행한다. 소리 모델은 대화 모델이 기기에서 돈 뒤에 다시 본다.

**2026-11-13 순서 변경**: P5(기기 추론)와 P6(통합)는 팀 앱 안에서 한다([연동 설계](../docs/app-integration/DESIGN.md)). v4는 보류다([미래 설계](../docs/future/v4-on-device-summary.md)).

**역할**: 설계·작업 배분·검수는 Claude, 구현은 Codex(기본 effort high, 추론이 많은 작업은 xhigh), 대화 작성과 기준선 판정은 agy(Gemini)가 맡는다. 음성 확보, 영상 승인, 청취 판정, 합성 훑어보기는 사람이 맡는다.

## 12. 위험과 결정 사항

| 위험 | 대응 |
| --- | --- |
| 합성 대화와 실제 대화의 차이 | 지름길 검사, 실제 dev로만 판단, 본보기 장면, 보조 경로(큰 모델 라벨) |
| 실제 평가 묶음이 적고 사람 판정이 주관적 | P0에서 아이+가족 100묶음 이상, test는 사람이 제안 없이 판정, `unsure` 따로 집계 |
| 평가 묶음에 맞춰 합성을 고치다 과적합 | dev와 test 분리, test는 최종에만 |
| 부정적인 분위기를 글만으로 못 가림 | 합성에 부정 유형과 밝은 짝을 넣어 학습, 실제 묶음에서 "부정" 메모가 달린 것의 오저장률을 따로 집계, 사용자 삭제로 보완 |
| 소리 모델(울음·고함이면 저장 취소)의 효과 미확인 | 보류(§6.2). mn10은 크기·속도·구분력이 충분하지만, 시험 소리가 차 안 실제 소리가 아니고 하품·기침을 울음으로 잡는 경우가 있어 정상 장면을 지울 위험이 있다. 사람이 승인한 영상에서 울음·고함 장면이 모이면 다시 시험 (T48, T48b 기록) |
| 두 모델을 함께 돌릴 때의 메모리·CPU | 소리 모델은 keep 후보 묶음에만 돌려 부담을 줄인다. 통합 뒤 AVD에서 함께 잰다 (T60) |
| 한 줄 순간을 글만으로 못 잡음 | 주 판정을 이진으로. 필요하면 음향 단서를 나중에 다시 검토 |
| 실제 차 마이크·주행 중 STT 제약 미확인 | P4에서 AVD 연속 측정, 실차와 Pleos 문서 확인은 사람이 |
| 아이 말의 전사 오류 | 망가뜨리기 규칙에 반영. 프로파일을 사람이 고친 기준 전사로 다시 잰다 |
| 음성 저장의 민감성 | 앱 전용 저장소, 기록 거부 소급 삭제, 저장 상한 |
| 영상 저작권 | 영상은 평가·참고에만, 원문·전사 비배포, 출처를 매니페스트에 기록 |

**결정된 것**

- 모델은 "남길 것 / 없음"을 가리는 후보 탐지기다. 이야기·한 줄 순간 구분은 참고 출력이다.
- 대상은 아이 + 가족 대화다(2026-11-12). 합성 카드의 75%가 이미 아이가 있는 장면이라 합성 쪽은 그대로 둔다. 모자란 것은 실제 평가 음성이다.
- 부정적인 대화(다툼, 혼내기, 험담, 안 좋은 소식)는 남기지 않는다.
- 학습은 합성 대화로 한다. 실제 영상은 흐름 참고와 평가에만 쓴다.
- 학습 글은 Pleos STT 모양으로 만든다. PC 쪽 기준 전사는 Whisper large-v3 긴 문맥 + 힌트다.
- 앱의 모델은 대화 모델(주)과 소리 모델(보조) 둘로 나눈다. 대화 모델을 먼저 넣고, 소리 모델은 자리만 두고 보류한다.
- 대화 모델의 탑재 후보는 글자 n-gram과 KoELECTRA-small 둘이다. 소리 모델의 후보는 EfficientAT mn10이다.
- Pleos STT는 앱 밖에서 돌므로 앱 메모리·CPU 예산에서 뺀다. 연속 수신 안정성은 통합 뒤 다시 확인한다.
- 수치는 실제 Pleos 묶음에서만 말한다.
- **평가 음성은 사람이 승인한 무편집 차 안 영상에서만 모은다.** 직접 녹음은 하지 않는다. 따라서 실제 차 마이크 조건과 부정적인 장면(영상으로 올라오지 않는다)은 검증하지 못한 채로 남는다.
- 대화 작성과 기준선 판정은 agy의 Gemini를 쓴다. API 키는 쓰지 않는다.
- **대화 모델은 M1이다**(2026-11-12). 탑재본은 int8 + 원래 문턱 0.957(2026-11-13).
- **팀 앱 연동이 먼저다(2026-11-13).** 데모의 요약 한 줄과 태그는 외부 LLM으로 만든다([연동 설계](../docs/app-integration/DESIGN.md)). 기기 안 요약·태그와 STT 견고성(v4)은 [미래 설계](../docs/future/v4-on-device-summary.md)로 보류했다.
- **소리 모델은 계속 보류하고, 그 메모리 몫을 요약 생성기에 쓴다**(2026-11-13). 부정 장면 걸러 내기보다 자연스러운 요약을 먼저 둔다.
- **STT 품질이 낮다고 저장 쪽으로 기울이지 않는다**(2026-11-13). 기록 거부를 놓칠 위험, 품질이 낮은 장면에 부정·소음 장면이 많을 가능성, 저장 상한 때문이다. "다시 들어볼 후보" 같은 별도 보관함도 지금은 만들지 않는다.
- Gleo AI는 쓰지 않는다(§1).

**결정이 필요한 것**

1. **묶음 일부만 이야기일 때**: 현재 초안은 "묶음 안 어디든 있으면 남김"이다. 이야기 8줄 뒤 용무 12줄이 이어지는 묶음을 남길지 확정이 필요하다.
2. **한 줄 순간을 계속 다룰지**: 이진 판정에서는 `keep`에 포함된다. 글만으로는 잘 안 잡히므로, 놓쳐도 되는 것으로 볼지 정한다.
3. ~~상황 태그~~: 데모는 외부 LLM이 고정 목록에서 고른다([연동 설계](../docs/app-integration/DESIGN.md)). 태그 목록 승인이 남았다.
4. **두 번째 판정자**: 사람 간 일치도를 잴 두 번째 사람.
5. **소리 모델을 넣을지**: 실제 차 안 울음·고함 음성으로 재시험한 뒤 정한다(§6.2).
6. **심사의 측정 범위**: 400MB·3%가 앱 프로세스만 재는지, Pleos STT까지 포함하는지 공모전 안내로 확인한다.
7. **태그 목록**: Claude가 초안을 쓰고 사람이 승인한다([연동 설계](../docs/app-integration/DESIGN.md) §5).
8. **요약 표시 단위**: 묶음마다 한 줄인지, 주행 하나에 제목 한 줄 + 묶음 목록인지. 화면 설계(PRD)와 함께 정한다.
9. **구절 인용을 화면에 보일지**: STT 오류가 그대로 보일 수 있다. 품질 점수가 높을 때만 보이는 안이 초안이다.
10. **날씨 신호**: Vehicle SDK에서 받을 수 있는지 확인한다.

## 13. v4 (미래 설계로 옮김)

v4(STT 견고성, 기기 안 요약 생성기, 태그·템플릿, 기록 거부 보조)는 2026-11-13에 보류하고 [docs/future/v4-on-device-summary.md](../docs/future/v4-on-device-summary.md)로 옮겼다. 지금은 팀 앱 연동이 먼저이고, 연동 데모의 요약·태그는 외부 LLM으로 만든다([docs/app-integration/DESIGN.md](../docs/app-integration/DESIGN.md)).
